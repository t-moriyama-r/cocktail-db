# 条件検索の意味

旧サイトの「カクテル検索」(条件検索)が、どの条件で何を返していたかと、新しい API の条件との対応をまとめる。新しい検索 API の実装(#163〜#167)と、旧と新の結果の突き合わせ(#169)は、この文書を基準にする。

- 旧の挙動の基準は本番の版(旧ソースの `laravel13/` と、画面のソース `laravel6/resources/js/`)。旧ソースは private の `t-moriyama-r/cocktail-legacy` にある(`CLAUDE.md` の「旧ソースの参照」)
- 「旧で確かめた結果」の数は、旧システムを手元で動かし(`docs/legacy-local.md`)、本番のデータのダンプに対して旧の `CocktailFactory::cocktailSearch` を呼んで出したもの(2026-10-26)。手元で動くのは Laravel 6 版の BE だが、検索のコード(`SearchController`・`app/Classes/`)は本番と同じ(cocktail-legacy の README の「本番との違い」)
- 新しい木での一致の意味は [#161] で決めた。中身は下の「新しい木での意味」の節にある。旧と結果が変わる条件は `docs/search-expected-diffs.md` にまとめる

## 旧の仕組み

| どこ | 旧ソース |
|---|---|
| API | `POST /api/cocktailSearch` → `SearchController@cocktailSearch` → `CocktailFactory::cocktailSearch` |
| 条件の検証 | `app/Http/Requests/Search/SearchCocktail.php` |
| フォーム用の木 | `POST /api/getKindsForForm` → `CommonController@get_kinds_for_form`(カテゴリとその子のミドルを全部、技法、種別を返す。整形は画面) |
| 画面(フォーム) | `components/Forms/Search/Cocktail/form.vue`。送る値は `Modules/cocktailSearchClass.js` に詰める |
| 画面(結果) | `components/Results/Tables/Cocktails.vue`(並べ替えは画面で行う) |
| もう 1 つの呼び出し元 | `components/Detail/component/AffiliateContainer.vue` の「このアイテムが使われているカクテルを探す」。`Modules/cocktailSearchClass_instant.js` に詰める |

旧の材料の分類は固定の 3 段で、レシピの材料の行(`t_recipies`)は次の列を持つ。

- `category`(カテゴリ。必須)
- `middle_category`(ミドル。カテゴリの子。null のときは「カテゴリしか指定していない」材料)
- `brand`(銘柄。検索の条件には使わない)
- `is_optional`(任意の材料)

カテゴリは種別(`m_category_kinds`)に属する: 1 蒸留酒・2 醸造酒・3 混成酒・4 ソフトドリンク・5 その他。

## 旧の条件

`SearchCocktail` の検証は次のとおり。

| 条件 | 検証 | 画面が送る値 |
|---|---|---|
| `searchMethod` | 必須(値は検証しない) | `or`(既定)/ `and` / `having` |
| `isEasily` | 必須・真偽値 | かんたん検索のチェック(既定は外れている) |
| `Method[]` | 必須・配列 | チェックした技法の ID(既定は全部) |
| `Category[]` | 必須・配列 | チェックしたカテゴリの ID |
| `Middle[]` | 配列(任意) | チェックしたミドルの ID。1 つも無ければ空の配列 |

`searchMethod` が 3 つのどれでもないと、カクテル ID の変数が作られずにエラーになる(画面からは送られない)。

### 材料の一致(`or`・`and`)

レシピの行 r が条件に一致するのは、次の両方を満たすとき。

- `r.category ∈ Category`
- `r.middle_category ∈ Middle`、または `r.middle_category` が null

つまり、カテゴリを選ぶと「そのカテゴリしか指定していない材料」と「選んだミドルの材料」が一致し、選んでいないミドルの材料は一致しない。ミドルを選ぶと、親のカテゴリしか指定していない材料も一致する。

- `Middle` が空の配列のときは、`whereIn` が常に偽になり、ミドルが null の材料だけが一致する
- `Middle=[999999]` は特別な値で、`or` のときだけ、ミドルを問わずカテゴリだけで一致させる。画面のフォームからは送られず、アフィリエイトの部品の「このアイテムが使われているカクテルを探す」だけが使う(下の「アフィリエイトの部品」)

旧で確かめた結果(カテゴリ 1 つ。子のミドルは 5 つ):

| `Middle` | 件数 |
|---|---|
| 子のミドルを全部 | 190 |
| `[999999]` | 190 |
| 子のミドルを 1 つだけ | 186 |
| 空の配列 | 160 |

### `searchMethod=or`(OR 検索)

一致する材料が 1 つでもあるカクテル。画面の説明は「チェックした『いずれか』が含まれているカクテルを検索」。

### `searchMethod=and`(AND 検索)

選んだカテゴリごとに、一致する材料があるカクテル(カテゴリの数だけ絞り込みを繰り返す)。画面の説明は「チェックした『すべて』が含まれているカクテルを検索」。

- 繰り返しの単位はカテゴリだけ。ミドルは各カテゴリの一致を絞る条件としてだけ効き、「選んだミドルごとに」は数えない。同じカテゴリの 2 つのミドルを選んでも、どちらか一方の材料があれば一致する
- 途中で 0 件になったら打ち切るつもりの `if(empty($ids)) break;` があるが、`$ids` はコレクションなので `empty()` は常に偽で、打ち切らない(結果は変わらない)

旧で確かめた結果: カテゴリ 2 つ(と、それぞれの子のミドルを全部)で 1 件。

### `searchMethod=having`(あるもの検索)

手持ちの材料で作れるカクテル。画面の説明は「『チェックが入ったものだけ』で作れるカクテルを検索("その他"は省略可能なので無視されます)」。

旧の実装は、作れないカクテルを除く形で書いてある。任意でない材料(`is_optional=0`)の行のうち、次のどちらかに当たる行を持つカクテルを除く。

- `category ∉ Category`、かつ材料のカテゴリの種別が 5(その他)でない
- `middle_category ∉ Middle`(`middle_category` が null の行は当たらない)

このため、次のようになる。

- 任意の材料は持っていなくてよい
- 種別「その他」の材料は、**ミドルを指定していないものだけ**持っていなくてよい。ミドルを指定した「その他」の材料は、そのミドルを選んでいないと作れない扱いになる(種別の除外は 1 つめの句にしか掛かっていない)。画面の説明(「その他は無視されます」)とは食い違う
  - 本番のデータでは、ミドルを指定した任意でない「その他」の材料が 465 行あり、445 件のカクテルが持つ
  - 旧で確かめた結果: すべてのカテゴリ・ミドルを選ぶと 4,786 件。そこから種別「その他」のカテゴリとその子のミドルを外すと 4,455 件に減る
- ソフトドリンク(種別 4)は持っている必要がある

旧の不具合([#165] で再現しないと決めた):

- カクテル ID を 1 から「カクテルの件数(下書きを含む)」までしか見ていない。ID が件数を超えるカクテル(消えたカクテルがあるので、新しいカクテルほど)は出ない
  - 旧で確かめた結果: 下書きを含む件数は 5,707 件、ID の最大は 6,732。すべてのカテゴリ・ミドルを選んだときの 4,786 件の ID の最大は 5,704。下書きでないカクテル 5,136 件のうち、ID が 5,707 を超える 350 件が出ない(4,786 + 350 = 5,136 で、残りがちょうどこれ)
- `Middle` が空の配列だと、`whereNotIn` が常に真になり、任意でない材料を持つカクテルがすべて除かれる
  - 旧で確かめた結果: すべてのカテゴリを選び、`Middle` を空にすると 0 件。画面では、子のミドルが無いカテゴリだけを選んだときにこうなる

### 3 つに共通の絞り込み

材料で選んだカクテルを、さらに次で絞る。

- `Method[]`: カクテルの技法がこの中にあるもの
- `isEasily` が真: `recipe_count` が 3 以下のもの(旧で確かめた結果: すべてのカテゴリ・ミドルを選んだあるもの検索で、4,786 件 → 2,283 件)。新で `recipe_count` が何を数えるかは [#154] で決めた(`docs/decisions/recipe-count.md`)
- 下書き(`is_draft=1`)は出さない

### 返すもの

条件に合うカクテルを全件と、その件数を返す。ページングは無い。並び順の指定(`ORDER BY`)は無く、旧で確かめた範囲では ID の昇順で返っていた(保証された並びではない)。

### 並べ替え(画面)

結果の表の見出しを押すと、画面が並べ替える。押すたびに昇順と降順が入れ替わる。

| 列 | 並べ替えに使う値 | 最初に押したとき | 補足 |
|---|---|---|---|
| 製法 | 技法の ID | 昇順 | |
| 名前 | 名前 | 昇順 | カタカナをひらがなに寄せて比べる |
| Name | 英名 | 昇順 | 小文字に寄せて比べる |
| ベース | ベースの名前 | 昇順 | カタカナをひらがなに寄せて比べる |
| 必須 | `recipe_count` | 昇順 | |
| 甘さ | 甘さ | 降順 | 値の無いものは、向きによらずいつも最後 |
| 評価 | 評価 | 降順 | 値の無いものは、向きによらずいつも最後 |
| 度数 | 度数 | 降順 | |
| 動画 | 動画の有無と、カクテルの更新日時 | 降順 | 動画の無いものは、向きによらずいつも最後。動画のあるものどうしは更新日時で比べる |

見出しを押すまでは、API が返した順のまま。

### 画面の入力の形(`form.vue`)

- 種別ごとに、カテゴリとその子のミドルがチェックボックスで並ぶ(種別の中は名前の順)。「メジャーでない項目」は既定で隠れていて、表示を切り替えられる
- カテゴリにチェックを入れると、子のミドルにすべてチェックが入る(隠れている「メジャーでない」ミドルも含む)
- ミドルにチェックを入れると、親のカテゴリにもチェックが入る。ミドルのチェックをすべて外しても、親のカテゴリのチェックは外れない
- カテゴリのチェックを外すと、子のミドルのチェックも外れる
- 結果として、「ホワイトラムを持っている」とミドルを選ぶと、親の「ラム」にもチェックが入り、「ラム(ミドル指定なし)」を求めるレシピも作れることになる
- 「全てチェック」は、「メジャーでない項目」を隠しているあいだは、メジャーなカテゴリ・ミドルだけにチェックを入れる。「全てはずす」はすべて外す
- 技法は既定ですべてチェックが入る。カテゴリと技法は 1 つ以上必須(画面でも検証する)。ミドルは 0 個でも送れる
- 検索方法(OR 検索・AND 検索・あるもの検索)はラジオボタン、かんたん検索はチェックボックス
- 条件はブラウザの localStorage に保存できる(「保存」「読み込み」と、前回の条件の「リロード」。キー `searchUser`・`searchInstant`)。新しい画面での保存は [#104]、旧の保存値の読み替えは [#175]

### アフィリエイトの部品

カテゴリ・ミドル・銘柄・カクテルの詳細ページにある部品の「このアイテムが使われているカクテルを探す」は、`Category=[そのカテゴリ]`・`Middle=[999999]`・`Method=[1〜6 すべて]` で検索する。詰める先(`cocktailSearchClass_instant.js`)はフォームとは別の部品で、`searchMethod` と `isEasily` を設定する箇所が無いので、いつも初期値の `or`・かんたん検索なしになる。

## 新しい条件との対応

新しい検索 API は `POST /api/cocktails/search` で、条件を JSON の本文で受ける([#163] の「追記: API の形」)。木は任意の深さになり、旧のカテゴリ・ミドルはどちらも木のノードになる([#29] で旧 ID と対応づける)。

| 旧の条件・挙動 | 新しい条件・挙動 | 決めた・決める issue |
|---|---|---|
| `POST /api/cocktailSearch` | `POST /api/cocktails/search`(JSON の本文) | [#163] |
| `searchMethod=or` | `mode=or`(既定) | [#163] |
| `searchMethod=and` | `mode=and`。材料はノードのまとまりの並びで受け、まとまりごとに 1 つの条件にする(決まったこと 6 の 1)。祖先と子孫を両方選んだら、深いほうだけ残して 1 つの条件にする(決まったこと 4) | [#164]・[#161]・[#282] |
| `searchMethod=having` | `mode=having` | [#165]・[#161] |
| `searchMethod` がそれ以外 | 検証で弾く(422)。`mode` に受けるのは、まだ受けている方式だけ(`and`・`having` は [#164]・[#165] が足すまで 422)。旧は値を検証せず、例外になっていた(`docs/search-expected-diffs.md` の「[#163] で変えたところ」) | [#163] |
| `Category[]`(2 段目) | `category_ids`(木のどのノードでもよい)。選んだノードの配下の材料も一致する(決まったこと 1)。空・省略は 422(旧と同じ)。1000 件を超えたら 422(認証の要らない公開 API に巨大な配列を送られて重くなるのを防ぐ。画面が選べるノードの総数より十分大きい)。無い ID・整数でない値が 1 つでもあれば 422(旧は検証を通り、何にも一致しなかった。`docs/search-expected-diffs.md` の「[#163] で変えたところ」) | [#163]・[#161] |
| `Middle[]`(3 段目) | `category_ids` に入れる(ミドルもノード)。選んだノードより大まかな指定(祖先)の材料も、どの方式でも一致する(決まったこと 2: A) | [#163]・[#161] |
| 「カテゴリを選び、一部のミドルだけ外す」(画面の自動チェックの結果) | 画面が残った子のノードに置き換えて送る。API に除外の条件は持たない(決まったこと 3: P) | [#161]・[#101]・[#102] |
| `Middle=[999999]`(ミドルを問わない) | 特別な値は持たない。カテゴリのノードを選べば配下も一致する(決まったこと 1)ので、ノード 1 つで同じ意味になる | [#161] |
| `Middle` が空の配列(`or`・`and` ではミドルが null の材料だけが一致) | 対応する条件は無い。ノードを選ぶと配下も一致する | [#161]・旧の保存値の読み替えは [#175] |
| `Middle` が空の配列(`having` で 0 件になる不具合) | 再現しない | [#165] |
| `having` で ID が件数を超えるカクテルが出ない不具合 | 再現しない | [#165] |
| `having` で任意の材料は持っていなくてよい | 同じ(決まったこと 5) | [#161]・[#165] |
| `having` で種別「その他」の材料は持っていなくてよい(ミドルを指定していないものだけ) | 「その他」の材料は持っていなくてよい(決まったこと 5)。ミドルを指定した「その他」の材料の扱いは、旧と変わる(下の「旧と変わるかもしれない点」)。新しい木で「その他」をどう見分けるかは [#153]・[#155] で決める | [#161]・[#165]・[#153]・[#155] |
| `having` でソフトドリンクは持っている必要がある | 同じ(決まったこと 5) | [#161]・[#165] |
| 銘柄は条件に使わない | 同じ。銘柄つきの材料は、所属するノードで一致する | [#161] |
| `Method[]`(必須) | `method_ids`。省略・`null`・空の配列なら、すべての技法として扱う。画面も、技法を 1 つも選ばなければすべての技法として送る(旧は押せなかった)。無い技法の ID は何にも一致しない(旧と同じ)。整数でない値・1000 件を超える配列は 422(`docs/search-expected-diffs.md` の「[#166] で変えたところ」) | [#166]・[#161]・[#282] |
| `isEasily`(`recipe_count <= 3`) | `is_easy`。真なら `recipe_count` が 3 以下(旧と同じ)。数え方は [#154] で決めた(`docs/decisions/recipe-count.md`)。省略・`null` なら絞らない(旧は必須。`docs/search-expected-diffs.md` の「[#166] で変えたところ」)。受ける値は旧と同じ真偽値(`true`・`false`・`1`・`0`・`"1"`・`"0"`) | [#166]・[#154] |
| 下書きは出さない | 同じ | [#163] |
| 全件と件数を返す。ページング無し | `page`・`per_page`(1〜50)でページングする。画面は 1 ページ 50 件で、ページを URL に残す | [#167]・[#282] |
| 並び順の指定無し(ID の昇順で返っていた) | 画面の既定の並びは ID の昇順([#282] の決まったこと 5)。同じ値のときは ID 順 | [#167]・[#282] |
| 画面で並べ替える(製法・名前・英名・ベース・必須・甘さ・評価・度数・動画) | `sort`(同じ列。値の名前は旧の画面の鍵と同じ)・`order`(`asc` / `desc`)でサーバーが並べ替える。比べ方は旧の画面と同じ。値の無いもの(英名も含む)は向きによらず最後(`docs/decisions/search-sort.md`) | [#167] |
| フォーム用の木(`getKindsForForm`。固定の 2 段) | `GET /api/search-form`(任意の深さの木) | [#95] |
| 画面の自動チェック(カテゴリ → 子のミドル、ミドル → 親のカテゴリ) | 親を選ぶと子孫もチェックされた表示になる。子をすべて外すと親のチェックも外れる(三状態のチェックボックス。旧は親のチェックが残った) | [#101]・[#282] |
| 条件の保存(localStorage) | 新しい画面での保存。旧と同じく、「読み込み」「リロード」を押したときだけ戻す | [#104]・[#175]・[#282] |
| アフィリエイトの部品の検索(いつも `or`・かんたん検索なし) | その材料のノードを選んだ `mode=or` の検索 | 呼び出し側の issue |

### 旧と変わるかもしれない点

[#169](旧と新の結果の突き合わせ)で「期待する差分」に書くかを決めるもの。この文書では決めない。

- **あるもの検索の、ミドルを指定した「その他」の材料**: 旧は、そのミドルを選んでいないと作れない扱いだった(本番のデータで、そのような材料を持つカクテルは 445 件。選び方によって、このうち新しく出る件数は変わる。たとえば、すべてのカテゴリ・ミドルから種別「その他」を外して選ぶと、旧は 4,455 件で、新は 4,786 件になり、差は 331 件)。[#161] の決まったこと 5・[#165] は「『その他』の材料は持っていなくてよい」としているので、そのまま実装すると、これらのカクテルが新しく出るようになる。[#161] では、深さによらず持っていなくてよいと決めた(「新しい木での意味」の決まったこと 6)

## 新しい木での意味

[#161] で決めたこと。決めた経緯と案ごとの比較は [#161] の本文とコメントにある。条件検索([#163]〜[#165])・別のカクテル([#174])・材料名からの検索([#173])は、どれもこの意味で一致を判定する。判定の部品は 1 か所([#162] の `IngredientMatch`)にまとめる。

### 例に使う木とカクテル

```
洋酒(根)
└ ラム
   ├ ホワイトラム ── 銘柄: バカルディ・スペリオール
   ├ ダークラム
   └ ゴールドラム
ソフトドリンク(根。役割 soft_drink)
└ コーラ / ソーダ
その他(根。役割 other)
└ 砂糖 / ミント / ライム
```

| カクテル | 材料(任意でないもの) |
|---|---|
| キューバ・リブレ | **ラム**(種類を指定しない)・コーラ・ライム |
| モヒート | **ホワイトラム**・ミント・砂糖・ソーダ |
| ダイキリ | **ホワイトラム(銘柄: バカルディ)**・ライム・砂糖 |
| ラム・コーク(濃いめ) | **ダークラム**・コーラ |
| マイタイ | **ホワイトラム**・**ダークラム**・… |

根の役割(`soft_drink`・`other`)は [#153] で決めた(`docs/decisions/category-root-role.md`)。材料に根は使わない([#153])。

### 決まったこと

1. **配下も一致する**: 「ラム」を選ぶと、配下(ホワイトラム・ダークラム・ゴールドラム)を使うカクテルも出る。例では 5 つすべてが当たる。旧も、カテゴリにチェックを入れると子のミドルがすべて付き、同じ結果になっていた
2. **より大まかな指定(祖先)も、どの方式でも一致する**(案 A): 「ホワイトラム」を選ぶと、種類を指定しない「ラム」を使うキューバ・リブレも、OR・AND・あるもの検索のどれでも出る。祖先は根の手前までたどる(根は材料に使わないので、根まで含めても結果は同じ)。旧も、ミドルを選ぶと画面が親のカテゴリにチェックを入れ、「カテゴリしか指定していない材料」が一致していた
3. **除外は API に持たない**(案 P): 「ラムを選び、ゴールドラムだけ外す」は、画面が残った子(ホワイトラム・ダークラム)に置き換えて送る。API の材料の条件は、選んだノードだけ(`or`・`having` は `category_ids`。`and` はノードのまとまりの並び。6 の 1)。子がすべてそろったら、画面が親 1 つに畳んで送る([#101]・[#102])
4. **AND で祖先と子孫を両方選んだら、深いほうだけ残す**(案 α): 「ラム」AND「ホワイトラム」は「ホワイトラム」1 つの条件になる。当たるのはモヒート・ダイキリ・マイタイと、2. によりキューバ・リブレ。画面が「ゴールドラム」を選んだときに送る「ラム」「ゴールドラム」も、条件になるのは「ゴールドラム」だけ(より細かい条件を優先する)
5. **あるもの検索で持っていなくてよい材料**: 任意の材料と、役割が `other` の根の部分木にある材料(「その他」)。ソフトドリンク(役割 `soft_drink`)は持っている必要がある。例で「ホワイトラム」だけを選ぶと、モヒートはソーダが、キューバ・リブレはコーラが要るので出ない。「その他」は深さによらず持っていなくてよい(旧の、ミドルを指定した「その他」の材料を持っている必要がある扱いは引き継がない。6 の 2)
6. **オーナーが決めたこと**([#161] の PR のコメントで返事をもらった)
   1. **AND の条件の単位は、まとまりごと**([#282] の決まったこと 1 で変えた。[#161] では「選んだノードごと」と決めていた)。画面が「同じ親から選んだもの」を 1 つのまとまりにして送り、まとまりごとに「どれか 1 つを使う」カクテルを探す。例: 「ラム」から「ゴールドラム」だけ外して「ホワイトラム」「ダークラム」を送ったら、2 つで 1 つのまとまりになり、どちらかを使うカクテル(モヒート・ダイキリ・ラム・コーク(濃いめ)・マイタイと、2. によりキューバ・リブレ)が当たる。旧の AND(根の直下のノード = カテゴリごとに 1 つの条件)と結果が同じになる。まとまりの単位と、深い木でまだ決めていないことは `docs/decisions/search-screen.md`
   2. **あるもの検索の「その他」は、深さによらず持っていなくてよい**(5. のとおり)。旧と結果が変わる(`docs/search-expected-diffs.md`)

### 一致の定義

選んだノードの集合を S とする。材料のノード n(銘柄つきの材料は、銘柄が所属するノード)が S と**一致する**のは、S のどれか s について、次のどちらかを満たすとき。

- n が s か、s の子孫(決まったこと 1)
- n が s の祖先で、根でない(決まったこと 2)

閉包表(`category_closures`)では、`ancestor_id ∈ S` の子孫と、`descendant_id ∈ S` の祖先(根を除く)を合わせた集合に n が入るか、で引ける。

| 方式 | カクテルが当たる条件 |
|---|---|
| `or` | S と一致する材料が 1 つでもある |
| `and` | S を、画面が送ったまとまり(決まったこと 6 の 1)に分け、まとまりごとに、そのまとまりと一致する材料がある。ほかのまとまりの祖先だけのまとまりは、子孫のまとまりに一致する材料が祖先のまとまりにも一致するので、除いても結果は同じ(決まったこと 4) |
| `having` | 持っていなくてよい材料(決まったこと 5)を除いた材料が、すべて S と一致する |

- `or`・`and` は、任意の材料も一致の対象に含める(旧と同じ。旧の `or`・`and` は `is_optional` を見ていない)
- 1 つの材料が、いくつかの条件を同時に満たしてよい(例: `and` で「ラム」の材料は、ラムの子孫のどの条件も満たす)。旧も、カテゴリしか指定していない材料 1 行で、そのカテゴリの条件を満たしていた
- 選ぶノードは根でもよい(画面が子をすべて選んだときに畳んで送る)。根を選ぶと、その部分木のすべての材料が一致する
- 銘柄は条件に使わない(旧と同じ)。ダイキリは所属ノードの「ホワイトラム」で当たる
- `method_ids` を省略したら(`null`・空の配列も)、すべての技法として扱う(旧は 1 つ以上が必須だった)

### 旧の条件との対応

旧の条件(カテゴリ C・ミドル M)を新しいノードの集合に直す規則は [#175] にある。カテゴリ c ごとに、次のとおり。

| c の子のミドルのうち M に入っているもの | 新しい S | 旧と新の結果 |
|---|---|---|
| すべて | c | 同じ(配下がすべて一致し、旧もすべてのミドルと「c だけを指定した材料」が一致した) |
| 一部 | 入っているミドル | 同じ(入っているミドルと、祖先の c だけを指定した材料が一致する。入っていないミドルは一致しない)。`and` では、入っているミドルが 1 つのまとまり(決まったこと 6 の 1)になり、旧の c の条件 1 つと同じになる |
| 1 つも無い | c | **変わる**。旧は「c だけを指定した材料」にだけ一致した。新しい規則では c の配下も一致する(`docs/search-expected-diffs.md`。[#282] の決まったこと 2) |
| (c に子のミドルが無い) | c | 同じ |

この規則で直すと、一致の判定は旧と同じになり、変わるのは上の「1 つも無い」の行と、あるもの検索の「その他」(決まったこと 6 の 2)だけになる。旧の不具合(上の「旧の不具合」)は別に [#165] が扱う。
