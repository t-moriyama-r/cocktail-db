# 条件検索の、旧と新で結果が変わる条件(期待する差分)

旧と新の条件検索の結果を突き合わせるコマンド([#169] の `legacy:compare-search`)は、ここに書いた差分で説明できないものだけを失敗にする。一致の意味は `docs/search.md` の「新しい木での意味」にある。

差分を足すときは、決めた issue ごとに節を分け、次の 3 つを書く。

- どの条件で変わるか(旧の条件の形で)
- どう変わるか(旧の結果・新の結果)。旧で確かめた件数があれば添える
- なぜ変えたか(決めた issue・PR)

ほかの差分は、決めた issue ごとに、その issue の PR がこの文書に節を足す。それまで、この文書は次のものを扱わない(`legacy:compare-search` に差分として説明がなければ、失敗になる)。

- 旧の不具合を再現しないもの: 下の「[#165] で再現しないもの」
- [#28] で移さないと決めた行: 消えたカクテルの材料の行(`docs/migration-anomalies.md` の 1)は、旧もカクテルが無いので結果に出ない。同じ材料の 2 行目(同じ 2)は、カクテルの集合を変えない。どちらも節は要らない。移行で直した行は、下の「[#28] で直した行」
- 旧の保存した条件の読み替え([#175]): 読み替えの PR が節を足す

### `legacy:compare-search` との対応

`legacy:compare-search` は、条件の組(`backend/tests/Fixtures/search-cases.json`)ごとに、旧の検索を旧 DB にそのまま流した結果と、下の節(`### ` の見出し 1 つが 1 つの差分)を旧の検索に当てた結果を出し、後者と新の結果が合わないカクテルだけを失敗にする。説明できた差分は、どの節で説明できたかを件数で出す。

- 節は `backend/app/Services/LegacySearchCompare/ExpectedDiff.php` の値と 1 対 1 で、見出しの文字列も同じにする(テストで確かめる)。節を足したら、そこにも値を足し、`LegacySearchReplay` に旧の検索への当て方を書く
- 条件の検証の差分([#163]・[#164]・[#166] の節)は、旧の画面が送る条件の形では起きないので、`legacy:compare-search` は扱わない(新の API のテストで確かめる)
- 本番の旧 DB に流すときは、デプロイが `tests/` を配らないので、`--cases` で条件の組のファイルを渡す

## [#161] で意味を変えたところ

### カテゴリを選び、その子のミドルを 1 つも選ばない(`or`・`and`)

- 条件: `Category` に c が入り、c に子のミドルがあり、そのどれも `Middle` に入っていない(旧の画面で、カテゴリにチェックを入れてから子のミドルをすべて外すと送られる)
- 旧: 「c だけを指定した材料」(`middle_category` が null)にだけ一致した
- 新: c を選んだ条件に直る([#175])ので、c の配下の材料も一致する。旧の `Middle=[999999]` と同じ結果
- 旧で確かめた結果: カテゴリ「ラム」だけで OR 検索すると、`Middle=[]` で 252 件、`Middle=[999999]`(ミドルを問わない)で 835 件。新では 835 件になる見込み
- 理由: [#161] の決まったこと 1(選んだノードの配下も一致する)。旧の「カテゴリだけを指定した材料にだけ一致する」は、新しい条件では表さない。画面でも、子をすべて外したら親のチェックが外れ、この条件は作れない([#282] の決まったこと 2。`docs/decisions/search-screen.md`)
- `having` で `Middle` を空にしたときは、旧の不具合で 0 件になる([#165] で扱う)

### あるもの検索の、ミドルを指定した「その他」の材料

- 条件: `having` で、種別「その他」のミドルを指定した、任意でない材料を持つカクテル(本番のデータで 445 件)
- 旧: そのミドルを選んでいないと作れない扱い(種別の除外がカテゴリの句にしか掛かっていない)
- 新: 「その他」の材料は深さによらず持っていなくてよいので、ミドルを選んでいなくても出る
- 旧で確かめた結果: すべてのカテゴリ・ミドルを選ぶと 4,786 件。そこから種別「その他」のカテゴリとその子のミドルを外すと 4,455 件に減る(新では減らない)
- 理由: [#161] の決まったこと 5・6 の 2(オーナーの判断)。文面は「任意の材料と『その他』は持っていなくてよい」で、旧の画面の説明(「"その他"は省略可能なので無視されます」)とも合う

## [#163] で変えたところ

条件の受け方と検証。一致の判定は変えていない。旧の値は、手元で動かした旧(`docs/legacy-local.md`)で `SearchCocktail` の検証と `CocktailFactory::cocktailSearch` を呼んで確かめた(2026-10-28)。

### 方式(`searchMethod` → `mode`)を省く

- 条件: 方式を送らない
- 旧: `searchMethod` は必須で、検証で 422
- 新: `mode` を省くと(`null` も)OR 検索になる
- 理由: [#163] の「やること」2(`mode` の既定値は `or`)

### 方式が `or`・`and`・`having` のどれでもない

- 条件: `searchMethod`(新は `mode`)に、それ以外の値を送る
- 旧: 値を検証しないので通り、検索の途中で `Undefined variable: ids` の例外になる(500)
- 新: 検証で 422
- 理由: `docs/search.md` の「新しい条件との対応」(それ以外の方式は検証で弾く。[#163])

### 無いノードの ID・整数でない ID

- 条件: `Category`(新は `category_ids`)に、無い ID か、整数でない値(`"abc"` など)を入れる
- 旧: 検証を通り、その値は何にも一致しない。ほかの ID があればその結果だけを返す(無いカテゴリ ID だけで 0 件、ラムと無い ID で 835 件、`["abc"]` で 0 件)
- 新: 1 つでも入っていれば、検証で 422
- 理由: [#163] の「受け入れ条件」(存在しない ID は 422)

### CSRF のトークン

- 条件: CSRF のトークン無しで検索を呼ぶ
- 旧: トークンが要り、無いと 419(`docs/legacy-local.md` の「はまりどころ」)
- 新: 要らない(認証の要らない公開 API で、結果は副作用の無い読み出し)
- 理由: [#163] の「追記: API の形」

### `category_ids` の件数の上限

- 条件: `category_ids` に 1001 件以上の ID を入れる
- 旧: 件数を制限しない
- 新: 1000 件を超えたら、検証で 422(1000 件までは受ける)
- 理由: 認証の要らない公開 API に巨大な配列を送られて、検証と検索が重くなるのを防ぐ(`docs/search.md`。レビューの指摘。[#163])

## [#164] で変えたところ

AND 検索の条件の受け方と検証。一致の判定は変えていない(まとまりごとの一致は [#282] の決まったこと 1。旧のカテゴリごとの条件と同じ結果になる)。旧の値は旧ソース(`CocktailFactory::cocktailSearch` の `and`)から読んだ見込みで、旧を動かして確かめてはいない。

### AND の材料の条件を、まとまりの並びで受ける

- 条件: `searchMethod=and` で `Category`・`Middle` を送る(新は `mode=and` で `category_groups`)
- 旧: `Category` のカテゴリごとに 1 つの条件にし、`Middle` は各カテゴリの一致を絞るだけ
- 新: 画面が送ったまとまりごとに 1 つの条件にする。旧の条件を直すときは、カテゴリ c ごとに、c(子のミドルがすべて入っているか 1 つも無いとき)か、入っているミドル(一部のとき)を 1 つのまとまりにする(`docs/search.md` の「旧の条件との対応」)。結果は旧と同じで、変わるのは [#161] の節の「カテゴリを選び、その子のミドルを 1 つも選ばない」だけ
- 理由: [#282] の決まったこと 1(`docs/decisions/search-screen.md`)

### AND で、無いノードの ID・整数でない ID

- 条件: `searchMethod=and` で、`Category`(新は `category_groups` のどれかのまとまり)に、無い ID か整数でない値を入れる
- 旧: 検証を通り、その値の条件を満たすカクテルが無いので 0 件(旧ソースからの見込み)
- 新: 1 つでも入っていれば、検証で 422
- 理由: [#163] の「受け入れ条件」(存在しない ID は 422)を、AND のまとまりにも当てた

### AND の ID の総数の上限

- 条件: `category_groups` の ID が全部で 1001 個以上
- 旧: 件数を制限しない
- 新: 検証で 422(1000 個までは受ける)
- 理由: `category_ids` の上限([#163] で変えたところ)と同じ。認証の要らない公開 API に巨大な配列を送られて、検証と検索が重くなるのを防ぐ

### AND のまとまりの個数の上限

- 条件: `category_groups` のまとまりが 21 個以上
- 旧: 件数を制限しない
- 新: 検証で 422(20 個までは受ける)
- 理由: 現実のカクテルの材料は 20 に届かない(#470 でオーナーが決めた)。ID の総数の上限(1000 個)だけだと、1 個ずつのまとまりを 1000 個送れて、まとまりごとの一致の判定が重くなる

## [#166] で変えたところ

技法(`Method[]` → `method_ids`)とかんたん検索(`isEasily` → `is_easy`)の受け方。絞り込みの意味(技法がこの中にあるもの・`recipe_count` が 3 以下)は変えていない。旧の値は、旧ソース(`SearchCocktail` の検証と `CocktailFactory::cocktailSearch`)を読んで書いた。旧を手元で動かして確かめてはいない。

### 技法を省く・`null`・空の配列

- 条件: 技法を送らない、または 1 つも入れない
- 旧: `Method` は必須(`required|array`)で、検証で 422
- 新: すべての技法として扱う(技法で絞らない)
- 理由: `docs/decisions/search-screen.md` の決まったこと 6(技法を 1 つも選ばないときは、すべての技法として送る。[#282])と、[#161] の補足(技法を省略したときは、すべての技法として扱う)

### 技法の ID に整数でない値

- 条件: `Method`(新は `method_ids`)に、整数でない値(`"abc"`・`1.5`・真偽値など)を入れる
- 旧: 検証を通り、その値は何にも一致しない(ほかの ID があれば、その技法の結果だけを返す)
- 新: 1 つでも入っていれば、検証で 422(無い技法の ID は、旧と同じく弾かずに何にも一致しない)
- 理由: `category_ids` の整数でない ID([#163] で変えたところ)とそろえ、API の型(整数の配列)と受ける値を合わせる。[#166] の PR で決めた

### 技法の件数の上限

- 条件: `method_ids` に 1001 件以上の ID を入れる
- 旧: 件数を制限しない
- 新: 1000 件を超えたら、検証で 422(1000 件までは受ける)
- 理由: `category_ids` の件数の上限([#163] で変えたところ)と同じ。認証の要らない公開 API に巨大な配列を送られて、検証と検索が重くなるのを防ぐ。[#166] の PR で決めた

### かんたん検索を省く・`null`

- 条件: `isEasily`(新は `is_easy`)を送らない
- 旧: `isEasily` は必須(`required|boolean`)で、検証で 422
- 新: かんたん検索なし(材料の数で絞らない)として扱う
- 理由: 旧の画面の既定(かんたん検索のチェックは外れている)と同じ結果にする。方式を省くと OR 検索になる([#163] で変えたところ)のと同じく、省いた条件は画面の既定で扱う。[#166] の PR で決めた

## [#282] で変えたところ

### あるもの検索で、カテゴリを選び、その子のミドルを 1 つも選ばない

- 条件: `having` で、`Category` に c が入り、c に子のミドルがあり、そのどれも `Middle` に入っていない。`Middle` は空でない(空なら下の「[#165] で再現しないもの」)
- 旧: c の子のミドルを指定した材料は、持っていない扱い(`middle_category ∉ Middle` の行を持つカクテルを除く)。c だけを指定した材料は、持っている扱い
- 新: c を選んだ条件に直る(`docs/search.md` の「旧の条件との対応」。[#175])ので、c の配下の材料も持っている扱いになる
- 旧で確かめた結果: なし(旧ソースから読んだ見込み)
- 理由: [#282] の決まったこと 2(`docs/decisions/search-screen.md` の「旧との差分」の、カテゴリにチェックがあり子のミドルが 0 個の保存値は親 1 つに直す)。`or`・`and` の同じ条件は、上の [#161] の節

## [#154] で変えたところ

### かんたん検索の材料の数

- 条件: `isEasily` が真(新は `is_easy`)
- 旧: 列 `recipe_count` が 3 以下のもの。列の値は、保存のときと数え直しのときで定義が混ざっている
- 新: 移行の後に、任意でなく「その他」でない材料の行の数で数え直した値が 3 以下のもの
- 旧で確かめた結果: かんたん検索に出る件数(`recipe_count <= 3`)は、旧の列の値のままで 2,640 件、数え直すと 2,886 件(`docs/decisions/recipe-count.md` の「かんたん検索の結果が変わる」)
- `legacy:compare-search` は、旧の材料の行を同じ定義で数え直し(移行と同じく、ミドルのある行はミドルの親の種別で見て、材料・銘柄・量まで同じ行は 1 行と数える)、その値で旧の検索を絞り直す
- 理由: [#154] の決まったこと 1(`docs/decisions/recipe-count.md` の「旧との差分」)

## [#28] で直した行

### ミドルの親とカテゴリが合わない材料の行

- 条件: ミドルの親が、その行のカテゴリと合わない材料の行(本番の旧 DB で 2 行。`docs/migration-anomalies.md` の 3)を持つカクテルが、そのカテゴリかミドルの親で一致するかどうかで結果が変わる条件
- 旧: 行のカテゴリの列で一致を見る(ミドルの親でないカテゴリを選ぶと一致する)
- 新: 移行でミドルの親に合わせたので、ミドルのノード(親のカテゴリの配下)で一致を見る
- 旧で確かめた結果: なし(旧ソースから読んだ見込み)
- 理由: [#28] の決まったこと(`docs/migration-anomalies.md` の 3。ミドルの親に合わせる)

## [#165] で再現しないもの

旧の不具合の詳しい説明と確かめた件数は `docs/search.md` の「旧の不具合」にある。

### あるもの検索で、ID がカクテルの件数を超えるカクテル

- 条件: `having`(旧の条件検索)で、下書きでないカクテルのうち ID が「カクテルの件数(下書きを含む)」を超えるもの
- 旧: 出ない
- 新: 条件に合えば出る
- 旧で確かめた結果: すべてのカテゴリ・ミドルを選ぶと 4,786 件。ID が 5,707 を超える 350 件が出ない
- 理由: [#165] の決定(旧の不具合は再現しない)

### あるもの検索で、`Middle` が空の配列

- 条件: `having` で、`Middle` を空にして検索する
- 旧: 0 件
- 新: 条件に合うカクテルが出る
- 旧で確かめた結果: すべてのカテゴリを選び、`Middle` を空にすると 0 件
- 理由: [#165] の決定(旧の不具合は再現しない)
