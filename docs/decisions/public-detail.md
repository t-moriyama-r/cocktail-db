# 公開の詳細ページで、旧と同じにできない表示

#283 で決めたこと。旧の画面(カテゴリ・ミドル・銘柄・カクテルの詳細、ヘッダー、ヘルプ)は、旧のカテゴリ・ミドルの 2 段に頼っていて、深さの決まっていない新しい木ではそのままにできない表示があった。その 6 つの表示と、問いにしなかった既定をここに置く。決めた経緯は #283 の本文とコメントにある(オーナーの回答は 2026-10-26 と 2026-10-29 のコメント)。

この文書でいう木の段は、次の例で書く。画面に出ない大元のノード(旧の種別。`docs/decisions/category-root-role.md`)を「大元」と呼び、その直下の段(旧のカテゴリにあたる。例の「ラム」)を「いちばん上の段」と呼ぶ。

```text
蒸留酒(大元。画面に出ない) > ラム(いちばん上の段) > (間のノード) > ホワイトラム > 銘柄: バカルディ
```

## 決まったこと

1. **カテゴリ詳細の「これを使ったカクテル」は、旧と同じくランダムの 5 件と「再取得」**。#174 のノード起点を使い、配下のノードを使うカクテルも当たる。全件のページングは出さない。全件を見たい人は、アフィリエイトの欄の「このアイテムが使われているカクテルを探す」から条件検索の結果へ行ける(旧と同じ)
2. **詳細ページの銘柄の一覧は、旧の意味を任意の深さに広げる**。#42・#43 の応答に足す
   - ノードの詳細: そのノードの配下すべて(自分を含む)に所属する銘柄
   - 銘柄の詳細: 「同じノードのほかの銘柄」(自分を除く)と、「親ノードの配下で、別のノードに所属する銘柄」の 2 つ
3. **材料・銘柄の所属は、いちばん上の段と、指定されたノード(末尾)だけを出し、銘柄はその後ろに書く**。間のノードは省く。オーナーが確かめた読み方:
   - ホワイトラムを使った材料 → 「ラム / ホワイトラム」
   - 銘柄つき → 「ラム / ホワイトラム (バカルディ)」
   - 材料のノードがいちばん上の段の「ラム」そのもの → 「ラム」だけ
   - オーナーの回答の「根」は、画面に出ない大元ではなく、いちばん上の段(「ラム」)のこと。API が返すパンくず(`docs/decisions/cocktail-detail.md` の決まったこと 4。先頭が大元)から、画面が先頭を除いた最初の段と末尾の段を選んで出す
   - 出した段は、それぞれノードの詳細へのリンクにする(#283 の案 A のまま。旧も各段がリンク)。銘柄は銘柄の詳細へのリンク
4. **ランダムウォーク(ヘッダーの「現在の登録数」のリンク先)の行き先は、カクテル・ノード・銘柄を 3 分の 1 ずつ**で選ぶ。旧の割合(ノードにあたるカテゴリとミドルで 2/4)には合わせない。#45 で作った(`GET /api/random-walk`)
5. **ログイン中に、公開の詳細ページから編集画面へ行く入口を作る**。ただし、公開の画面から管理者のログイン状態を問い合わせる処理が要るので、この issue では作らず、別の issue で作る(issue は人が立てる)。別の issue の中身の例: ログイン状態の問い合わせ、カクテル・ノード・銘柄の詳細のタイトルを編集画面へのリンクにする、ヘッダーに「>>TOP」「ログアウト」を出す
6. **`/helpme` は、「管理者ページのログインにtwitterアカウントを用います」の一文を、新しいログイン(パスキー)に合わせて直して写す**。about のページは作らない(サイトの紹介はトップのメニューにある)

### 既定(問いにせず、旧と同じにしたもの)

- カテゴリ詳細で子のノードが 0 件のときも欄を出し、旧の「ミドルカテゴリの登録なし」にあたる文を出す。見出しと文言は「子のノード」に合わせる
- カクテル詳細の「材料が似たカクテル」「同じベースのカクテル」は、0 件でも見出しを出す
- 銘柄の度数が無いときは、旧と同じ形(`Strength:%`)で出す

## 旧との差分

テストの表では `差分あり(意図: docs/decisions/public-detail.md)` としてここを指す。#283 の本文の「旧との差分(意図: #283)」と同じ中身。

- 材料・銘柄の所属: 旧は「ラム/ホワイトラム」(カテゴリ/ミドル)、銘柄があれば「ラム(バカルディ)」(ミドルを省く) → 新は銘柄があっても「ラム / ホワイトラム (バカルディ)」とミドルにあたる段を省かず、間のノードだけ省く(決まったこと 3)
- 銘柄の一覧: 旧はカテゴリ詳細にカテゴリの銘柄すべて(配下のミドルの分を含む)、ミドル詳細にそのミドルの銘柄、銘柄詳細に同じミドルのほかの銘柄と同じカテゴリの別ミドルの銘柄を出していた → 新は任意の深さで、ノード詳細にそのノードの配下すべて(自分を含む)の銘柄、銘柄詳細に同じノードのほかの銘柄と親ノードの配下の別のノードの銘柄を出す(決まったこと 2)
- ランダムウォーク: 旧はカクテル・カテゴリ・ミドル・銘柄を 4 分の 1 ずつ → 新はカクテル・ノード・銘柄を 3 分の 1 ずつ(決まったこと 4)
- `/helpme`: 旧は「twitterアカウント」でログインすると書いていた → 新はパスキーに合わせて直す(決まったこと 6)

## 理由

1. 旧の見た目(5 件と「再取得」)を保つため。全件は条件検索の結果で見られるので、詳細ページでページングしなくても、見られなくなるカクテルは無い
2. 旧で見えていた銘柄を失わないため。旧のカテゴリ詳細は配下(ミドル)の銘柄もすべて出し、銘柄詳細は同じミドルの銘柄と同じカテゴリの銘柄を分けて出していた。直下だけ(#283 の案 B)にすると、深い木では一覧が空に近くなる
3. 深い木でパンくずを全部つなぐと材料の表の 1 行が長くなる。旧の表でも出していたのは 2 段(カテゴリ・ミドル)までなので、いちばん上の段と材料のノードの 2 段に収める。銘柄があってもミドルにあたる段を残すのは、どの種類の銘柄かが材料の行だけで分かるようにするため(オーナーの指定)
4. 新ではカテゴリとミドルが 1 つの「ノード」になったので、種類ごとに同じ割合で選ぶ(オーナーの選択)
5. 直したいものを見つけたその場で編集画面に行けると、データの手直しが楽なため。公開の API はセッションを使わない(`docs/decisions/cocktail-detail.md` の決まったこと 2)ので、ログイン状態を公開の画面から知る仕組みを別に作る必要があり、決めるだけのこの issue の範囲を超える
6. 新の管理画面のログインはパスキー(`docs/decisions/passkey.md`)で、旧の文のままでは事実と違う。about は旧でも開けなかった(ルートが無い)ので、作らなくても旧から失うものは無い

## 決まったことに書かれていないこと

#283 では決めていない。それぞれの issue で、旧の挙動を確かめて決める(旧と変えるなら「旧との差分」を置く)。

- **銘柄の詳細の「親ノードの配下で、別のノードの銘柄」に、親ノードの直下に所属する銘柄を入れるか**: 旧は、ミドルのある銘柄の詳細では、カテゴリの直下(ミドルなし)の銘柄を入れていなかった(上の表の `getFromCategoryExceptMiddle`。SQL の NULL の扱いによるもので、意図したものかは分からない)。決まったこと 2 の言葉どおりなら入る(親ノード自身も「別のノード」)。旧のデータでこの差が画面に出るか(カテゴリの直下の銘柄と、ミドルのある銘柄が同じカテゴリにあるか)は確かめていない(未確認)。#43 で扱う
- **銘柄の一覧の見出し**: 旧の「〈ミドル〉の銘柄の一覧」「〈カテゴリ〉銘柄の一覧」を、新でどのノードの名前で出すか(親ノードか、いちばん上の段か)。#54 で扱う
- **ランダムウォークの「ノード」に、大元のノードを入れるか**: 旧の種別は詳細ページが無く、行き先にならなかった。新の大元には詳細ページがある(#105)。#45 で、旧と同じく大元のノード(根)は行き先に入れないことにした(旧の行き先はカテゴリとミドルで、新の根でないノードにあたる)
- **`/helpme` の、ログインの一文のほかの箇所**: 「2.twitterアカウントを持っている方。」の見出しと、「その他のログイン方法は僕が使わないので実装してません。パスワードリセットを…」の文も旧のログインのことを書いている。決まったこと 6 は 1 文だけを挙げている。連絡先の「twitterのDMかなんかで教えて下さい」はログインの話ではない。#57 で扱う
- **決まったこと 3 の形を、材料・銘柄の所属のほかにも使うか**: 名前検索の結果のノードの「親」の列は、#52 の本文で決まったこと 3 の形(根を除いた祖先のうち、いちばん上の段とすぐ上の親)にした(`docs/decisions/name-search.md` の「結果の画面(#52)」)。決まったこと 3 は材料・銘柄の所属について決めた
- **「Material」の列(英名)の書き方**: 旧は日本語の列と同じ形で英名を出していた。#108 の本文も同じ形としている。#283 では日本語の書き方だけを決めた
