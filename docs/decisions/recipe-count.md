# 材料の数(`recipe_count`)の定義と持ち方

#154 で決めたこと。`recipe_count` は、かんたん検索(材料 3 個以下)と、検索結果の表の「必須」の列に使う。

## 決まったこと

1. **定義**: `recipe_count` は、カクテルの材料のうち、**任意でなく**、**役割が「その他」の根(#153)の部分木に入っていない**ものの数。かんたん検索は「その他を除いて 3 個以下」になる
2. **持ち方**: `cocktails.recipe_count` の列に持ち、**`RecipeCounter`(#156)だけが更新する**。更新のきっかけは次のとき
   - カクテルの材料を保存したとき(#130)
   - 部分木を根をまたいで移したとき(「その他」の根に出入りすると数が変わる。#122)
   - 銘柄の所属ノードを変えたとき(#64)
   - 旧 DB からの移行(#31)
   - 数え直しのコマンド(#74)
3. 旧の保存のときの数え方(「その他」も数える)は移さない

## 旧との差分

テストの表では `差分あり(意図: docs/decisions/recipe-count.md)` としてここを指す。

- カクテルを保存したときの `recipe_count`: 旧は任意でない材料を「その他」も含めて数えていた → 新は「その他」の根の部分木の材料を数えない(決まったこと 1)
- かんたん検索(`recipe_count <= 3`)に出るカクテル: 旧は保存のときと数え直しのときで定義の混ざった列の値で絞っていた(2,640 件) → 新は決まったこと 1 の定義(下の「旧 DB で確かめた事実」の定義 2)で数え直した値で絞る(2,886 件。下の「かんたん検索の結果が変わる」)
- 検索結果の表の「必須」の列と、その並べ替え: 旧は上の混ざった値を出していた → 新は決まったこと 1 の定義で数え直した値を出す

## 理由

- **定義**: あるもの検索では「その他」(ガーニッシュなど)を持っていなくてよい材料として扱っている(#153)。材料の数も「その他」を数えないほうが、「3 個そろえば作れる」というかんたん検索の意味と揃う。旧で一括の数え直し(`sys/genrec`)に使っていたのもこの定義
- **持ち方**: かんたん検索の絞り込みと「必須」の列の並べ替えで毎回数えると、材料の表を集計する分だけ検索が重くなる(#96)。列に持つと、書き換える処理が散らばるとずれるので、更新は 1 か所(`RecipeCounter`)に寄せる。ずれていないかは `data:verify`(#157)で確かめる

## 旧ソースで確かめた事実

本番の BE(`laravel13/`)と画面(`laravel6/resources/js/`)を読んだ。

| どこ | 何をしているか |
|---|---|
| 保存のとき: `RecipeCalc::recipe_count`(`FactoryHelper` のカクテルの保存から呼ぶ) | 画面から送られた材料の配列のうち、`is_optional` が無いか false のものを数える。**種別を見ないので「その他」も数える**(定義 1) |
| 数え直し: `SystemController::insertRecipeCols` → `calRecipeCount`(ルート `sys/genrec`。ログインが要る) | 全カクテルについて、`t_recipies` のうち `is_optional = 0` で、`m_category.kind <> 5`(その他)のものを数えて上書きする(定義 2) |
| かんたん検索: `CocktailFactory::cocktailSearch` | `isEasily` のとき `recipe_count <= 3` で絞る。列の値をそのまま使い、その場では数えない |
| 検索結果の表: `Results/Tables/Cocktails.vue` | 「必須」の列に `recipe_count` を出し、並べ替えにも使う |

- 除いていたのは種別 5(その他)だけ。種別 4(ソフトドリンク)は、どちらの数え方でも数える
- どちらの数え方も材料の**行**を数える。同じ材料が 2 行あれば 2 と数える
- 保存のときの数え方は、画面から送られた配列を数えるので、カテゴリの入っていない行も数える(度数の計算 `calcStrength` はその行を飛ばす)。画面が空の行を送ることがあるかは確かめていない(未確認)

## 旧 DB で確かめた事実

手元に復元した本番の旧 DB のダンプ(カクテル 5,707 件)で数えた。

| 数えたもの | 件数 |
|---|---|
| `recipe_count` が定義 1(任意でない材料すべて)と合わない | 1,425 |
| ― そのうち定義 2 とは合う | 1,424 |
| `recipe_count` が定義 2(任意でなく、その他でない材料)と合わない | 744 |
| ― そのうち定義 1 とは合う | 743 |
| どちらの定義とも合わない | 1 |
| 定義 1 と定義 2 で数が違うカクテル | 2,168 |
| `recipe_count` が、材料の**全行**(任意・その他も含む)の数と合わない | **1,580** |

- **#28 の「`recipe_count` が実際のレシピ数と合わない 1,580 件」は、上の最後の数え方(任意の材料も含めた全行と比べる)と一致する**。どちらの定義と比べた数でもない。#28 がどの SQL で数えたかは記録に無いので、同じ SQL だったとは言い切れない
- 合わないもののほとんどは、2 つの定義が混ざっていることによる(定義 1 と合わないものの 1,424 件は定義 2 と合い、定義 2 と合わないものの 743 件は定義 1 と合う)。`RecipeCounter` で数え直せば揃う
- どちらとも合わない 1 件は、`recipe_count` が 7 で、材料の行が全部で 6 行しかない
- 更新日時が 2019 年のカクテルは定義 2 と合うものが多く、2020 年以降は定義 1 と合うものが多い(2019 年: 4,248 件のうち定義 1 と合う 2,834・定義 2 と合う 4,003。2020 年: 1,268 件のうち 1,267・814)。いつ数え直しが走ったかまでは、この数からは分からない
- `t_recipies.is_optional` は 0 か 1 だけ(任意は 222 行)。材料のカテゴリはすべて `m_category` にあり、材料の無いカクテルは無い

数えた SQL:

```sql
-- 定義 1: 任意でない材料をすべて
SELECT COUNT(*) FROM t_cocktails c
WHERE c.recipe_count <> (SELECT COUNT(*) FROM t_recipies r WHERE r.cocktail_id = c.id AND r.is_optional = 0);
-- 定義 2: 任意でなく、その他(kind 5)でない材料
SELECT COUNT(*) FROM t_cocktails c
WHERE c.recipe_count <> (SELECT COUNT(*) FROM t_recipies r JOIN m_category m ON r.category = m.id
                         WHERE r.cocktail_id = c.id AND r.is_optional = 0 AND m.kind <> 5);
-- 材料の全行(任意・その他も含む)。1,580 件になる
SELECT COUNT(*) FROM t_cocktails c
WHERE c.recipe_count <> (SELECT COUNT(*) FROM t_recipies r WHERE r.cocktail_id = c.id);
```

## かんたん検索の結果が変わる

定義 2 で数え直すと、かんたん検索に出るカクテルが旧と変わる。旧の列の値のままでは 2 つの定義が混ざっているため。

| | かんたん検索に出る件数(`recipe_count <= 3`) |
|---|---|
| 旧(列の値のまま) | 2,640 |
| 定義 2 で数え直した後 | 2,886(+246) |
| (参考)定義 1 で数え直した場合 | 2,149 |

これは決まったことによる意図した差分で、回帰ではない。

## 決まったことに書かれていないこと

- 同じ材料が 2 行あるカクテルを 1 と数えるか 2 と数えるか。旧はどちらの数え方も行を数える(2)。#28 では、材料・銘柄まで同じ行が 16 組あり、量が同じなら移行で 1 行にまとめる案になっている。#156 の受け入れ条件の「同じ材料が 2 行あるカクテルで、定義どおりの数になる」は、この点が決まってから確かめる
