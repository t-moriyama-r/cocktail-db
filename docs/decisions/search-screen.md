# 検索画面で、旧と同じにできない動きの扱い

#282 で決めたこと。決めた経緯と案ごとの比較は #282 の本文とコメントにある。

検索画面(#51 とその子の issue)を旧の画面(`Forms/Search/Cocktail/form.vue`・`Results/*`・`Modules/localStorageHelper.js`)と突き合わせると、新しい木(任意の深さ。#161 の決まったこと)では旧と同じにできない動きと、issue が旧と違う動きを前提にしているところがあった。そのうち 6 つをオーナーが決めた(1〜5 は A、6 は B)。一致の意味そのものは `docs/search.md` の「新しい木での意味」にある。

例に使う木: 洋酒(根) └ ラム └ ホワイトラム / ダークラム / ゴールドラム。カクテルは、キューバ・リブレ(材料: ラム 種類の指定なし)、モヒート(ホワイトラム)、マイタイ(ホワイトラムとダークラムの両方)。

## 決まったこと

1. **AND 検索で、親を選んで子を外したとき**: 画面が「同じ親から選んだもの」を 1 つのまとまりにして送り、API(#164)はまとまりごとに「どれか 1 つを使う」で探す。例: 「ラム」から「ゴールドラム」だけ外して AND 検索すると、ホワイトラム・ダークラムが 1 つのまとまりになり、モヒートもマイタイも(祖先の一致で、キューバ・リブレも)出る。旧と同じ結果
   - API の材料の条件は、AND では `category_ids` の並びから「まとまりの並び」に変わる。項目は `category_groups`(ノードの ID の並びの並び。例: `[[ホワイトラム, ダークラム], [コーラ]]`)で、`mode=and` のときだけ受ける(#164)。API は送られたまとまりのとおりに探し、まとまりの単位は画面が決める
   - 旧から移した 3 段の木(根・旧のカテゴリ・旧のミドル)では、まとまりは次のとおりになる。旧の AND がカテゴリごとに 1 つの条件だったのと同じ
     - 同じカテゴリの子のミドルは、1 つのまとまり(ミドルを 1 つずつ選んでも同じ。旧は `checkParent` が親のカテゴリにチェックを入れ、カテゴリの条件 1 つになった)
     - 根の直下のカテゴリは、それぞれが 1 つのまとまり(「ラム」と「ジン」を両方選んだら、両方を使うカクテル)
   - まとまりの中で一致は、`docs/search.md` の一致の定義(配下も、根でない祖先も一致する)のまま。「ラム」と「ホワイトラム」のように祖先と子孫が別のまとまりになっても、子孫のまとまりに一致する材料は祖先のまとまりにも一致するので、#161 の決まったこと 4(深いほうだけ残す)と同じ結果になる
   - **深い木でのまとまりの単位**(#304 のオーナーの判断で決めた): 根の直下のノードごとに 1 つのまとまり。旧のカテゴリの単位と同じ。送る ID(親を選んで子を外すと残った兄弟になる)を、木で根の直下のどのノードの配下かで分ける。まとまりを作る関数は #304 の `toSendGroups`
     - 例: 洋酒(根) └ ウイスキー └ スコッチ └ シングルモルト / ブレンデッド、ウイスキー └ バーボン で、「ウイスキー」を選び「ブレンデッド」だけ外すと、送る ID はシングルモルトとバーボンで、1 つのまとまり(どちらか)
     - 差が出るのは、根の直下のノードの下が深く、別々の分類を選ぶとき。洋酒 └ スピリッツ └ ラム └ ホワイトラム、スピリッツ └ ジン └ ドライジン で「ホワイトラム」と「ドライジン」を別々に選ぶと、スピリッツが根の直下のノードなので 1 つのまとまり(どちらか)になる。「根でない同じ親ごと」にする案なら 2 つ(両方)になった。この木(根・旧のカテゴリ・旧のミドル)では、根の直下は旧のカテゴリなので起きない
     - 不採用: 根でない同じ親ごとに 1 つのまとまりにする案。深い木で親を選んで子を外すと、残った兄弟が段ごとに別の条件になり、子を 1 つ外すと結果が減る
   - OR・あるもの検索は、まとまりを見ない(選んだノード全部の和で探す)。結果は変わらない
2. **親にチェックを入れたあと、子をすべて外したとき**: 最後の 1 つを外したら、親のチェックも外れる(ふつうの三状態のチェックボックス)。旧の「親だけ」(カテゴリしか指定していない材料にだけ一致する)の条件は作れない
   - 旧サイトの保存値(#175・#290)にこの状態(カテゴリにチェックがあり、子のミドルが 0 個)があれば、親 1 つに直す。旧より広くなる(`docs/search-expected-diffs.md` の「カテゴリを選び、その子のミドルを 1 つも選ばない」)
3. **「全てチェック」と「メジャーでない」材料**: 旧と同じく、見えているものだけを選ぶ。「メジャーでない」材料を隠しているあいだに押すと、隠れている材料は選ばれず、隠れていた選択は外れる
   - 部分木がすべて選ばれたときだけ親に畳めるので、送る ID は根の数個にならず、多くなる(数百になりうる)。#102 の URL の 2,000 文字に収まるかは、作るとき(#304・#102)に確かめる
4. **保存した条件の復元**: 旧と同じく、「読み込み」「リロード」のボタンを押したときだけ戻す。検索画面を開いたときに自動では戻さない(いつも既定の状態で開く)
5. **結果一覧**: 1 ページ 50 件。既定の並びは ID の昇順。並べ替えとページを URL に残し、戻るボタンで同じ並び・同じページに戻る
6. **技法(製法)を 1 つも選ばないとき**: 検索できる。0 個ならすべての技法として送る(API は技法を省くとすべての技法として扱う。#161 の補足・#166)

### 既定(問いにしなかったもの。旧と同じにする)

- 0 件のときの文言は、旧と同じ「カクテル検索結果 0件ヒットしました。」と、見出しの行だけの表(#103)
- 甘さの表示で「中甘」が出ない旧の不具合と、度数が無いときに `0.0` と出る旧の表示は、旧と同じにする(直すなら別の issue で決める。#298)
- 旧サイトの保存値を直す API は POST にする(#290。#163 と同じ理由で、ID が数百になりうる)

### 決めていないこと

なし。

## 旧との差分

テストの表では `差分あり(意図: docs/decisions/search-screen.md)` としてここを指す。

- 親にチェックを入れたあと子をすべて外したとき: 旧は親のチェックが残り、「カテゴリしか指定していない材料」にだけ一致する条件になった → 新は親のチェックも外れ、その条件は作れない(決まったこと 2)
- 親にチェックを入れて子を 1 つ外したとき: 旧は親のチェックが残る → 新は親が「一部」(三状態。決まったこと 2)
- 兄弟のある子を 1 つだけ選んだとき: 旧は親にもチェックが入る(`checkParent`) → 新は親が「一部」で、親にはチェックを入れない(決まったこと 2。#101 の追記に「親に自動でチェックを入れる必要はない」とある)
- 旧サイトの保存値で、カテゴリにチェックがあり子のミドルが 0 個のもの: 旧は「カテゴリしか指定していない材料」にだけ一致した → 新は親 1 つに直し、配下の材料も一致する(決まったこと 2)
- 結果一覧の件数: 旧は全件を 1 枚に出した → 新は 1 ページ 50 件で、ページと並べ替えを URL に残す(決まったこと 5)
- 技法を 1 つも選ばないとき: 旧は「製法は必須です。」と出て検索ボタンを押せなかった → 新は検索でき、すべての技法として送る(決まったこと 6)

1・3・4 は旧と同じ結果・同じ動きにする決まりなので、差分は無い。5 の既定の並び(ID の昇順)は、旧で返っていた並びと同じ(旧は並びを指定していなかった)。

## 理由

1. 旧と結果が一致し、旧との突き合わせ(#169)も楽になる。「残った兄弟を別々の条件にする」(B)だと、子を 1 つずつ足すと結果がどんどん減り、最後の 1 つで親に畳まれた途端に増える。利用者から見て不自然で、旧からの退行に見える。#164 の作業(API の形の変更)が増えるのは受け入れる
2. 見た目(子は全部外れている)と結果がそろう。親のチェックを残して親を送る(B)と、子のカクテルも出て、見た目と結果が食い違う。#175 の直し方(ミドルが 0 個なら親 1 つ)とも合う
3. 旧と結果が同じで、利用者の見ていない材料を勝手に選ばない
4. 前の条件が残っていることに気づかずに検索する、ということが起きない。ボタンも旧のまま引き継げる
5. 旧は全件を 1 枚に出していたが、新の API(#167)は 1 回に最大 50 件。全件を画面でつなぐと、数千件で表示が重い。既定の並び(ID の昇順)は、旧で返っていた並びに近い(`docs/search.md` の「返すもの」)
6. オーナーの判断(#282 のコメント)。既定ではすべての技法にチェックが入っているので、0 個にするのは利用者が自分で外したときだけ

## 旧ソースで確かめた事実

画面のソース(`t-moriyama-r/cocktail-legacy` の `laravel6/resources/js/`。本番の画面のビルドのもとはこの版。cocktail-legacy の README の「本番との違い」)を読んだ。行番号は `components/Forms/Search/Cocktail/form.vue` のもの。

| どこ | 何をしているか | 関わる決まったこと |
|---|---|---|
| `clickedCategory`(355〜377 行目) | カテゴリにチェックを入れると、子のミドルにすべてチェックを入れる(隠れている「メジャーでない」ミドルも)。外すと、子のミドルのチェックもすべて外す | 1・2 |
| `checkParent`(379〜385 行目) | ミドルにチェックを入れると、親のカテゴリにもチェックを入れる。ミドルのチェックをすべて外しても、親のカテゴリのチェックは外さない(コメントに、外れないようにわざと算出プロパティにしなかったとある) | 1・2 |
| `check_all`(327〜343 行目) | 「メジャーでない項目」を隠しているあいだは、メジャーなカテゴリ・ミドルだけを選び、選択をそれで置き換える(隠れていた選択は外れる) | 3 |
| `mounted`(212〜230 行目)・`init`(298〜317 行目) | フォームの部品を取り終えたら `init` で既定の状態(技法はすべて・材料なし・OR 検索・かんたん検索なし)にする。localStorage は読まない。保存値を読むのは「読み込み」「リロード」のボタン(23・31 行目)だけ | 4 |
| `validateObj`(273〜285 行目)と 111〜119 行目・166 行目 | 技法(`method`)とカテゴリ(`category`)を `required` で検証し、失敗しているあいだは検索ボタンを押せない。技法の文言は validatorjs の日本語(183 行目の `useLang('ja')`)の `method` を「製法」に置き換えて出す | 6 |
| BE の `CocktailFactory::cocktailSearch`(`laravel13/`) | AND は、選んだカテゴリごとに 1 つの条件。ミドルは各カテゴリの一致を絞るだけ(`docs/search.md` の「`searchMethod=and`」) | 1 |
