# 楽天の商品検索 API のクライアント(`RakutenClient`)の決定

#72 で作る、楽天市場の商品検索 API(`docs/rakuten-api.md`)を呼ぶクライアント `App\Services\Affiliate\RakutenClient` で決めたこと。旧は `App\Classes\Factory\RakutenFactory::generateFromWord`(と、値を持つ `App\Classes\Rakuten`)。呼ぶ側(名前で探して保存する #248・商品のコードで取り直す #249)は、まだ無い。

## 決まったこと

1. 持つ操作は 2 つ
   - `searchItems(語, ジャンル)`: 語で探し、検索結果の先頭の 1 ページを楽天の順で返す。ジャンルの既定は旧と同じ `510915`(ビール・洋酒)。`null` を渡すとジャンルで絞らない。どの商品に `null` を渡すか(#155 の「洋酒ではない」の述語を使うか)は、呼ぶ側の #248 で決める(このクライアントでは決めない)
   - `getItem(商品のコード)`: 商品のコード(`shop:1234` の形)で 1 件を取り直す。売り切れも取る(`availability=0`)。見つからない(404・0 件・別のコードの商品だけが返る)ときは `null`
2. 設定(`App\Support\Settings`)から読むもの: アプリ ID(`rakuten.application_id`)・アクセスキー(`rakuten.access_key`)・アフィリエイト ID(`rakuten.affiliate_id`。前からある)。アプリ ID とアクセスキーは秘密の項目(規約 第5条でアプリ ID を他人に知られないよう管理するとあるため。`docs/decisions/settings.md`)
   - アプリ ID かアクセスキーが無いあいだは、楽天に問い合わせない。`searchItems` は `null` を返す。`getItem` は、見つからない(`null`。#249 が商品のコードを消す)と取り違えないよう、例外 `RakutenNotConfiguredException` を投げる。呼ぶ側は先に `isConfigured()` で確かめる
   - アフィリエイト ID が無ければ `affiliateId` を付けずに呼ぶ(そのとき楽天は `affiliateUrl` を返さないので、商品のページは `itemUrl`)
3. 取る項目は旧と同じ。商品名(`itemName`)・価格(`itemPrice`)・商品のページ(`affiliateUrl`)・画像(画像があるとき(`imageFlag` が 1)だけ、`smallImageUrls` の先頭から `?_ex=` 以降を取り除いた URL)。旧に無いものとして、商品のコード(`itemCode`)と販売できるか(`availability`)も持つ。検索結果のページへのリンクは、前からある `AffiliateSearchUrls::rakuten` が組み立てる(旧の `Rakuten::set_searchURL` と同じ形)
4. 失敗の分け方
   - 429(上限)・5xx(全体の上限・メンテナンス)・つながらない: `RakutenRetryLaterException`(次の回にまわす)
   - 対象のデータが無い 404(`not_found`): 0 件として扱う
   - それ以外の 4xx(パラメーターの誤り・アプリ ID やアクセスキーの誤り): `RakutenApiException`(楽天の `error` を持つ)
   - つながらないときの例外の文には、元の例外の文(アプリ ID の入った URL を含みうる)を入れない
5. アクセスキーは、URL(アクセスのログに残りうる)に載せず、ヘッダー `accessKey` で送る(どちらでもよいと公式にある。`docs/rakuten-api.md` の 2)
6. 呼べるのはアプリ ID ごとに 1 秒に 1 回まで(`docs/rakuten-api.md` の 5)。同じクライアントからの呼び出しは、前の呼び出しから 1 秒たつまで待ってから送る。別のプロセスとのあいだは揃えない(収集は 1 つのコマンドから順に呼ぶ想定。#248・#249)

## 確かめていないこと

- この PR を作った環境からは楽天のサイトにつながらず、公式のリファレンスを読み直せていない。呼び出し先・版・パラメーター・エラーは `docs/rakuten-api.md`(2026-10-26 に公式で確かめたもの)に合わせた
- 版 `20260701` の formatVersion=2 の応答の形(`Items` が商品の一覧で、`smallImageUrls` が URL の文字列の一覧)は、旧(`20170706`)の読み方と、`docs/rakuten-api.md` の 7 の出力の項目に合わせた。新しい版で形が変わっていないかは、実際に呼んで確かめていない
- エラーの本文の形(`error`・`error_description`)も、旧の版の形に合わせた
- 商品のコードで取ったときに、消えた・売り切れた商品で 404 が返るのか 0 件の 200 が返るのか(`docs/rakuten-api.md` の 6)。どちらでも `null` になるようにした
- 語の空白で 400 になる条件(空白で区切った語が短すぎるときと読んでいる)。旧のコメントにある推測のまま

## 旧との差分

- 呼び出し先: 旧は `app.rakuten.co.jp` の版 `20170706` に、アプリ ID だけを付けて呼んでいた → 新は `openapi.rakuten.co.jp` の版 `20260701` に、アプリ ID とアクセスキーを付けて呼ぶ(旧の呼び先と版は 2026-05-14 に止まった。`docs/rakuten-api.md` の 1)
- 証明書: 旧は TLS の証明書を確かめずに呼んでいた → 新は確かめる
- やり直し: 旧は 1 回目がどんな理由で失敗しても、空白を取り除いた語ですぐに 1 回やり直していた → 新は、400 が返って語に空白があるときだけ、1 秒空けてやり直す。429・5xx・つながらないときはやり直さず、次の回にまわす(1 秒に 1 回の上限があり、上限を超え続けると利用を止められうるため。`docs/rakuten-api.md` の 5)
- 呼ぶ間隔: 旧は取り直しのときだけ、1 件ごとに 1 秒待っていた → 新は、名前での検索も含めて、前の呼び出しから 1 秒空ける(同じ理由)
- 設定が無いとき: 旧はアプリ ID が無くても空のまま呼び、失敗して例外で止まっていた → 新は呼ばない(判断表の JC-04 による。意味の無い呼び出しをしない)
- 画像の URL に `?_ex=` が無いとき: 旧は画像の URL が空の文字になっていた(`strstr` が false を返すため) → 新は URL をそのまま使う(判断表の JC-04 による。壊れた値を保存しない)
- `affiliateUrl` が空・無いとき: 旧はそれをそのまま商品のページにしていた → 新は `itemUrl` を使う(判断表の JC-04 による。リンク先の無い商品を出さない)
